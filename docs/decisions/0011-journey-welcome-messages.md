# 0011 "ברוך הבא למסע": WhatsApp to registered travellers

**Context (spec block "ברוך הבא למסע", Sahar 24/10/2026):** the spec fires on a deal closed won with a registration attached. In this CRM the registration is usually created or updated AFTER the sale is won, so a deal-close trigger alone would miss most cases. Sahar decided: the trigger is the registration status; 'משוריין' sends the seat-reserved template, 'שולמה מקדמה' or 'שולם במלואו' sends the welcome template; never twice to the same person for the same message; the customer AND every passenger with a phone; no retro sends.

**Decision:**
1. Event `registration.changed` (outbound_webhooks, migration 054) on: registration INSERT or status change into one of the three; a non-primary passenger added or given a phone; the linked sale moving to 'נסגר בהצלחה'. n8n `TRAX - ברוך הבא למסע` (kENOh7fdnPaZmYbl) waits 30 s and calls `cloudchat-bridge {action:'journey'}`.
2. The send waits for the linked sale to be won (`whatsapp_journey_require_sale_won`, default true, Sahar's approved recommendation). A registration with no sale is not blocked.
3. Dedupe table `journey_messages` keyed (registration, kind, phone). Only `sent` is final; skipped (test mode, no template, missing trip data, sale not won) and failed rows are retried by the next event, so a later event still sends. `claim_journey_message()` makes the claim atomic, so two events in parallel cannot both send. Deposit then full payment are the same kind (welcome): one message. A seat-reserved message is never sent after a welcome.
4. Never send an empty variable: trip name, destination and departure date are required, plus every placeholder used in the template mapping. Missing data opens ONE urgent task on the registration (owner of the sale) and a notification, instead of a half-filled message.
5. On a send: note on the customer, customer status 'לקוח פעיל', CloudChat subscriber fields crm_customer_id / crm_registration_id / crm_journey_name / crm_registration_status (so Max knows this is a registered traveller, not a lead). Meta rejections are picked up by `sync` from /flow/error-logs and mark the row failed.
6. The spec's "drop the days sentence under 7 days" cannot be done inside one fixed Meta template; `{days_to_trip}` is always the whole number. Either the template omits it, or two template variants are needed (decision with the portal).
